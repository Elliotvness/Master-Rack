07Canonical data model

7.1 The rule the model exists to enforce

Architecture principle

There is one canonical, revision-pinned project model. The plan and elevation preview, the validation results, the assumptions, the BOM/takeoff, the client package, the internal quote package, the generated documents and the audit history are all derived from the same revision. There are no independent screen-only models. A configuration change either updates every derived output or it updates none of them.

Concretely this means the revision is the only thing that is stored as fact. Everything downstream is a function of it:

derive(revision) → { layout, findings, assumptions, bom, displayList }

Derived rows are persisted (they are expensive and we need them queryable), but they are caches with a provenance key, not sources of truth. Each derived row carries the revision_hash and engine_version it was produced under, and any row whose key does not match the current revision is invalid and is recomputed rather than displayed. This is the mechanism that makes "no screen-only model" enforceable rather than aspirational.

7.3 Value representation

Three conventions, all lifted from the reference projects because they were the hardest-won lessons there:

  1. Fixed-point integers, stored in micrometres. Lengths are integer µm; loads and capacities are integer millipounds. Division that is not exact is refused; quantities that must be split are allocate()d so the remainder goes somewhere explicit rather than into floating-point drift. rack-studio/packages/units is a complete, 100%-branch-covered implementation of the pattern, based on mil — the base changes, the mechanics do not.
  2. Why micrometres and not millimetres. One inch is 25.4 mm exactly, so every published inch value is a whole number of µm (48″ = 1,219,200 µm; the 5.92″ beam face = 150,368 µm) and every whole millimetre is a whole number of µm. Integer millimetres cannot do this: 48″ is 1219.2 mm, and rounding it to 1219 reads back as 47.9921″, which no longer matches the published lookup key. 18 of the 21 published spans miss their own key under integer-mm storage, silently turning every lookup off-grid and destroying the one behaviour the engine is built around (§10.4). Micrometres give a metric base with none of the loss.
  3. Unit and origin travel with the value. A number is {value, unit, origin}, where origin ∈ INPUT | DERIVED | CATALOG | RULE | UNKNOWN. Adding two values with different units raises rather than silently converting — because a silent foot-to-inch conversion puts a number in a package that nobody entered.
  4. Per-basis units are not convertible. A capacity published "per pair" is lb/pr, and converting it to lb is refused, because in a general-purpose unit library that conversion is a silent no-op that turns a per-pair capacity into a per-beam one. rack-engine/model/quantity.py encodes this as BASIS_BOUND; it is worth carrying over verbatim.

7.4 Canonical serialisation and hashing

The revision's content_hash is SHA-256 over a canonical JSON encoding: sorted keys, fixed number formatting, undefined dropped, explicit units, and a bounded recursion depth that fails loudly rather than truncating — a truncating hash is the one failure mode a hash must not have.

The hash covers content only. Lineage, timestamps, author and note are explicitly excluded, and that exclusion list is held as data so a test can assert it. Two revisions with identical content therefore have identical hashes, which is what makes "did this edit actually change anything?" a one-comparison question and what lets the artifact cache key be sha256(revision_hash ‖ catalog_release ‖ rule_pack ‖ engine_version). Including engine_version in that key is deliberate: a bug fix must invalidate every cached artifact, because that is precisely how you find out which issued documents were affected.

Honest limit

SHA-256 here gives tamper evidence, not tamper proofing. It detects modification to anyone holding a later head hash. It does not stop a database superuser. That is why the head is anchored externally (§13.4) and why customer-facing copy must say "tamper-evident, externally timestamped and independently re-verifiable" and never "tamper-proof".

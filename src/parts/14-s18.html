OD-20 can wait — and here is what deferring actually costs

Nothing technical. Phase 0 is tenant plumbing, row-level security, authorization, DTOs and the audit chain; none of it is client-specific and none of it changes based on who the pilot is. MVP-1 can be built end to end without a named client.

The cost is not rework — it is that MVP-1 gets built against assumptions instead of against one real building. The later a pilot appears, the less they shape the product, and the longer the central premise goes untested: that a client will actually do this configuration work themselves. Practical middle ground — start Phase 0 now, name the pilot before D-03 (the option builder), which is the first task where a real client's requirements would change what you build.

18.3 The two answers that need a second pass

OD-06 — why the storage base changed

The dual display is accepted as answered. The metric storage base cannot be millimetres, and this is arithmetic rather than preference: 48″ is 1219.2 mm, and an integer-mm store rounds it to 1219, which reads back as 47.9921″ and no longer matches the published lookup key. 18 of the 21 published spans miss their own key that way, turning every capacity lookup silently off-grid and destroying the one behaviour the engine is built around.

Integer micrometres solve it: an inch is 25.4 mm exactly, so every published inch value and every whole millimetre lands on a whole µm. That delivers the metric backend the answer asked for with no loss. Mass is asymmetric — the pound converts to metric exactly but not the reverse — so store integer millipounds and render kg as a derived, one-way display value.

OD-17 — answered, and re-cut against the source quotes

A job audit, then a second pass reading the eight source quotations. Two of four structural racking jobs involve material with no published capacity — one entirely used, one mixed. By component count, material value and pallet position the share is about 7%, but a single job is 91% of the volume sample, so those figures are not stable and the job count is the number that should govern: the failure this product can cause is per client, per job, and tonnage is the wrong denominator for a client-experience question.

Used-versus-new is a property of a component, not of a job. The all-used job still purchases new end-of-aisle protectors; the mixed job reuses and buys within the same component type, and its scope block reconciles exactly — reused plus newly purchased equals installed, on every line. There is no job-level flag that would be correct, which is why the reference sits on the BOM line as part_revision_id XOR uncatalogued_part_id and the new uncatalogued_part entity has no capacity column at all. Absent by schema rather than blank by convention, so no future code path can fill it in.

The quotes also produced the clearest evidence yet for the product itself. One job appears across three artifacts — a drawing and two quote revisions — carrying three different pallet-position counts, with a major scope reduction between revisions and nothing linking any of them to a shared model. A second job states two mutually inconsistent position counts on the same line of the same quote. This is the thesis of §1 evidenced from real paperwork rather than argued from first principles.

The matcher is still worth building in Phase 2; the derate still is not. At half of all jobs an estimator aid saying "this is dimensionally consistent with part X — go verify" clearly earns its place. It must not transfer that part's published capacity onto the client's material, with or without a reduction: a used-material derate has no published basis, so it caps at SECONDARY tier, which §11.2's ceiling limits to engineering review required regardless of any click.

The three questions nobody has asked yet

Across all four reference projects, two validation gates were repeatedly deferred and never closed: no PE has been asked whether this output is a useful input to them, and no drafter has confirmed which step of their workflow this actually removes. For Rack Master Studio there is a third, and it is the one the entire business case rests on: will a client actually do this configuration work themselves? A tool that shifts work to someone who refuses to do it does not save the work — it adds a support channel. OD-20 is how that gets answered. It is cheap to answer now and expensive to discover late.

The single thing to get right first

Two decisions in this document are structural and get exponentially more expensive to retrofit: BOM lines reference a part revision, never a part, and the derivation is deterministic with every implicit input made explicit. Everything else here — the audit chain, the tier ceilings, the issue register, even the tenant isolation — can be added later with effort. Those two cannot. Build them in week one and the rest of this blueprint stays achievable.

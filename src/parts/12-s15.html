15Phased roadmap and a tightly scoped MVP

15.1 Phase overview

PhaseGoalShipsExplicitly not in it
Phase 0
Foundations		Make the invariants structural before there is anything to leakRepo, kernel packages, tenant plumbing, RLS + CI assertions, authz middleware with boot-time route coverage, DTO layer + leakage contract test, audit table with append-only trigger and hash chainAny UI beyond a smoke page
MVP-1
The narrow loop		Prove the whole loop end to end for one option templateThe eight steps in §15.2Everything in §15.4
Phase 2
Make it usable at real scale		Handle the "three units, six options" case a real client bringsColumn and tunnel resolution, undo/redo, RFI loop, revision diff, cross-unit comparison, document issue register, internal takeoff export, where-used, catalog supersede impact viewPricing, DXF, client exports beyond PDF
Phase 3
Commercial depth		Close the loop into quotingC-revision release workflow, quote BOM with the as-configured → as-quoted diff, cost and margin behind a narrower role, contractual document generationAutomatic pricing without a human
Phase 4
Breadth		Beyond selective rack and beyond one manufacturerAdditional option templates, multi-manufacturer catalog abstraction, internal DXF, engineering calculation packageAnything claiming approval or compliance

Phase 0 is not overhead. Tenant plumbing, the DTO layer and the audit chain get exponentially more expensive to retrofit — they touch every route and every table. The leakage contract test in particular is worth ten times more written against six routes than against two hundred.

15.2 MVP-1 — the eight steps, and nothing else

#StepRequirementsDone when
1An internal user creates a client organization and project and sends an invitationFR-AD-01, FR-CT-*The invited address receives a link; the invitation row holds the org, role and a hash of the token.
2The client accepts, sets a credential, enrolls a second factor, and signs inNFR-SEC-02..05The token is single-use; a second redemption renders the same page as an expired one.

15.4 What MVP-1 explicitly does not contain

ExcludedWhyEarliest
Advanced CAD editing on the canvasThe value is in the model and the workflow, not in reimplementing a drafting tool.Phase 3 (FR-CP-13)
AutoCAD / DXF integrationUnverified: no DXF writer has been validated against a real AutoCAD seat, and no drafter has confirmed the output is usable without rework. Internal-only whenever it lands.Phase 4
Public self-signupThe invitation model is the access-control model. Public signup would require a completely different abuse and verification posture.Not planned
Automatic pricingEvery rate in the reference projects is an uncited "SoCal 2026 ballpark" and has never been back-tested against a live vendor quote. Automating an unvalidated rate is worse than no pricing.Phase 3
Broad multi-vendor catalogsOne manufacturer's data has already taken three passes to reach a trustworthy state. Multi-vendor multiplies the verification burden, not the code.Phase 4
Engineering calculationsOut of scope by product definition. No FEA, no Direct Strength Method, no seismic from first principles, in any phase.Not planned
Detailed customer BOM / DWG exportsThis is the value we are protecting. Giving it away defeats the product's purpose.Not planned
Cost, margin and discount dataNot needed to prove the loop, and every day it does not exist is a day it cannot leak.Phase 3
ImpersonationThe highest-risk feature in the product. It should not be built until the audit and authorization layers have been exercised in production.Phase 2

16Test strategy, acceptance criteria and demo scenario

16.1 Test layers

LayerWhat it provesNotes
Kernel unit testsArithmetic, refusals, provenance walking, canonical hashing100% branch coverage enforced on kernel-units, kernel-derive and kernel-checks. These are cheap, pure, and where correctness actually lives.
Property testsInvariants that examples misse.g. hashing is order-independent; allocate() always sums to the original; adding a level never decreases position count.
Golden fixturesKnown inputs produce known derived values within a stated toleranceModelled on rack-studio/fixtures, which stores mil, inches, a formula and a deltaMil against a 10-mil tolerance for each expected value. Wire them into the test run — in the reference project they are produced by a script that no test consumes.
Contract testsNo forbidden field on any client-reachable route; the positive companion for staffRoute enumeration is automatic, key inspection is recursive, the forbidden list is one shared constant.
Authorization testsEvery route rejects unauthenticated and wrong-tenant callers with 401/404Also enumerated automatically.
RLS testsSet a tenant context, attempt a cross-tenant read and a cross-tenant write, assert empty and refusedRun against a real Postgres, not a mock.
Determinism harnessHistorical submissions re-render byte-identicallyNightly. Failure means an unintended engine change or a leaked implicit input.
End-to-end walkthroughThe eight MVP steps as one executable transcriptThe single most valuable test in the suite. rack-studio/e2e/mvp.walkthrough.test.ts is a working model.
Accessibility auditContrast measured over rendered text nodes in both themes; keyboard traversalSelf-tests against known ratios before reporting, so a broken audit cannot pass silently.
Visual and markup checksEvery rendered drawing is well-formed; no literal colour appears in drawing code; both themes define the same tokensCheap, and catches a class of defect assertions cannot.

16.2 Acceptance criteria for MVP-1

Each is a named test that must be green to call MVP-1 done.

IDAcceptance criterion
AC-01An invitation token is redeemable exactly once. A second redemption, an expired token, a revoked token and a nonexistent token all produce the same page, the same status code and comparable timing.
AC-02A client principal calling every enumerated client route receives no response containing any key on the shared forbidden-field constant, at any nesting depth. That constant covers every row marked Hidden in §9.2: cost, unit_cost, landed_cost, buy_price, price, margin, margin_pct, discount, supplier, supplier_id, mpn, manufacturer_part_number, bom, bom_line, item_snapshot, capacity, capacity_case, catalog_release, source_document, page_ref, catalog_page_ref, digitised_by, approved_by, citation, verification_tier, rule_id, internal_note. One constant, used by the test, the log redactor and the response validator.
AC-03A client principal requesting another organization's project, revision or submission receives 404, not 403, on every route.
AC-04With the tenant context set to organization A, a raw SELECT against every tenant-scoped table returns zero rows belonging to organization B, and a cross-tenant INSERT is refused by WITH CHECK.
AC-05Every table in the application schema has row-level security enabled and forced, with at least one policy per operation. Adding a table without one fails CI.
AC-06Adding a route without an authorization policy declaration prevents the application from starting.
AC-07An unestablished value is never rendered as a numeral — in the UI, in the display list, or in a generated PDF. A refusal in the engine that leaks a number into the interface is not a refusal.
AC-08An off-grid span returns both brackets and no capacity value, and the trace states that the engine does not interpolate and why.
AC-09Used or generic material yields no capacity, and its trace carries no table basis at all — because no table was read.
AC-10Submitting with an open blocker is refused, and the refusal lists every reason, not the first.
AC-11After submission, UPDATE against the revision row fails at the database layer, and the application-level edit path throws.
AC-12The BOM for a submitted revision regenerates byte-identically from the revision alone, twice, on two machines.
AC-13Every BOM line carries a non-null part_revision_id, a rule text, a confirmed flag, and source object ids — or is an unresolved line with a non-null reason. There is no third state.
AC-14Deriving an internal revision leaves the source submission's content_hash unchanged, and the derived revision is absent from every client-facing response.
AC-15Every state change and every refused transition writes an audit event in the same transaction; the hash chain verifies from genesis.
AC-16A generated client PDF contains the watermark, the full disclaimer text, the P revision code and the short-form manifest hash on every page.
AC-17Deactivating a user terminates their sessions immediately and revokes their pending invitations.
AC-18A catalog release cannot be pinned, and fails the build, if any of these hold: approved_by is null; approved_by == digitised_by; or the release carries neither a recorded full cross-check nor a two-path reconciliation and has only one human signature. A machine digitiser identity does not by itself satisfy the second-party requirement.
AC-19Every check whose governing rule is below PRIMARY tier returns at most the ceiling for that tier. A check cannot be written that returns PASS against a secondary-sourced rule.
AC-20All eight MVP steps run as one automated walkthrough, ending with a byte-identical BOM regeneration and a frozen, deep-immutable submission.

16.3 Demo scenario

One narrative, roughly twelve minutes, that exercises every claim in this document. Build the seed data for it in Phase 0 so it is runnable from the first week.

#BeatWhat it demonstrates

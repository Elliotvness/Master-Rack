06Recommended web architecture and rationale

6.1 The shape

A conventional server-rendered/SPA web application on a managed Postgres, with one unconventional and load-bearing decision: the derivation kernel is a single pure module, compiled once, that runs unchanged in the browser and on the server. The browser runs it for the live preview; the server runs the identical module when a submission is frozen and when the internal BOM is produced. There is no second implementation to drift.

This is the direct lesson of the four reference projects. rack-takeoff has the same 126 lines of takeoff math byte-identically triplicated across three HTML files. rack-studio has a typed packages/ tree with roughly five checks and a single-file prototype with eleven, neither a superset of the other. rack-app and rack-engine are divergent siblings of one rack_core. Every one of those splits happened because deriving on the screen and deriving for the output were different code paths.

6.2 Stack recommendation

LayerRecommendationWhy this, here
UnitsInteger micrometres for length, integer millipounds for load. US Customary displayed primary, metric in parentheses, derived one-way and never re-parsed as input.Exact for every published inch value and every whole millimetre, so the no-interpolation lookup survives the dual-unit requirement (§7.3).
LanguageTypeScript end to end, strict plus noUncheckedIndexedAccess and exactOptionalPropertyTypesThe kernel must run in the browser. One language removes the second implementation. The strict flags are already proven in rack-studio.
FrontendReact with a file-based router (Next.js or Remix/React Router), two separate applications — client and internal — built from a shared component libraryTwo bundles is the cheapest structural guarantee that internal DTO types and field names are never present in a client bundle — a single app with conditional rendering ships them in the JavaScript. It does not by itself stop an internal value in an API response; that is what the seven layers in §14.6 are for.
APIREST/RPC with a generated OpenAPI schema; not GraphQLGraphQL's value is client-driven field selection, which is exactly the property we are trying to eliminate. If GraphQL is ever adopted, it must be two schemas behind two endpoints.
DatabasePostgreSQL 16+, managed. Migrations owned by a migrator role; the app runs as a non-owning app_user with no BYPASSRLS.RLS is the backstop; ownership separation is what makes RLS real.
Query layerA thin query builder (Kysely / Drizzle) over hand-written SQL, not a heavyweight ORMEvery query must be reviewable for its tenant predicate. Lazy-loading ORMs generate queries nobody reviewed — that is where over-fetch leaks come from.
JobsTransactional outbox in Postgres + a worker poolAn audit event and its business change must commit together; an email must not be sent for a transaction that rolled back.
Object storageS3-compatible with versioning and Object Lock in Compliance modeSubmission manifests must survive an insider with database access. Compliance mode cannot be overridden by the account root.
DocumentsServer-side PDF from the same display list the canvas drawsOne display list, three renderers (canvas, SVG, PDF). A drawing that prints differently from the screen is a support burden and a liability.
RenderingCanvas 2D with batched Path2D for the plan; inline SVG for elevationsMeasured in rack-studio/spikes/canvas-throughput: batching took whole-building draw from 6.80 ms to 3.30 ms p95. Elevations are small and benefit from SVG's text and accessibility.
PythonDeferred. Not in MVP-1 and not in phase 2.The only genuine case for it is DXF via ezdxf and a stamped calc package via ReportLab/WeasyPrint. Both are out of scope. Introducing a second runtime before it is needed buys a deployment problem and no capability.

6.3 Decisions this architecture makes, and what it rejects

DecisionChosenRejected, and why
Deployment shapeMulti-tenant web applicationDesktop application — rack-studio ADR-012 item 1 chose this. It is incompatible with a client-facing self-service product and is explicitly reversed here (§17.5).
IdentityPerson-level identity with organization membershipWorkstation identity (rack-studio ADR-013 item 1) and network-layer-only access via Tailscale (rack-engine ADR-014). Neither can name a person or scope an organization.
Tenant isolationShared database + RLS + explicit predicatesDatabase per tenant — internal staff need cross-organization views, which would become an N-database fan-out. Kept as a config-level escape hatch for a single enterprise client who demands it.
Internal data protectionPhysically separate *_internal tables with their own policyField filtering in the serializer — that converts a visible query bug into an invisible serialization bug. A client-facing query cannot leak what it cannot join to.
Configuration engineConstraint layer for choices + pure parametric functions for quantitiesOne big rule engine — ordering-dependent production rules are why configurators become unexplainable. Separating "what" from "how many" is what makes the greying-out explainable and the arithmetic auditable.
AuthorizationOne exhaustively tested authorize(actor, action, resource) function, table-driven, behind one middlewareAn external policy engine (OPA/Cedar/OpenFGA) — for five roles and one relationship chain it adds a network hop and a tuple-consistency problem for a policy set that fits in one file. Revisit at ~50 rules or when clients demand custom roles.
SessionOpaque server-side sessions in cookiesStateless JWT — server-side revocation is mandatory, which means server state exists anyway. JWTs are for machine-to-machine.
Catalog formatDeclarative JSON/TOML validated against a schemaExecutable Python loaded with runpy.run_path (rack-engine/catalog/loader.py) — acceptable for one vendored file in an internal tool, unacceptable the moment a catalog file could be uploaded.

    display-list/        renderer-neutral drawing model    (pure)
    render-canvas/  render-svg/  render-pdf/
    contracts/           OpenAPI schema + shared DTO types
    db/                  migrations, RLS policies, policy CI assertions
  data/
    catalog/<mfr>-<rev>/ manifest.json + parts + capacity tables
    rules/<pack>-<rev>/   manifest.json + rules
  fixtures/
    golden/              derivation fixtures with expected values and tolerances
    submissions/         historical manifests for the determinism harness
  tools/
    check-boundaries     no kernel package may import I/O, a framework, or an app
    check-rls            every tenant table has RLS enabled, forced, and a policy
    check-routes         every route declares an authorization policy
    check-leakage        no client-reachable route emits a forbidden field
    check-determinism    re-render historical manifests, assert byte-identical

The five tools/ checks are not nice-to-haves. Each one guards an invariant that a human reviewer will eventually miss, and each is cheap to write now and impossible to retrofit meaningfully once there are two hundred routes. rack-studio already ships working versions of the boundary checker and a provenance linter, including self-tests that write a violation and assert it is caught — port that pattern.

08API and service boundary recommendations

8.1 Two API surfaces, not one with flags

The single highest-leverage API decision is to expose two separate route namespaces backed by two separate DTO families, rather than one namespace whose responses vary by role.

/api/client/v1/...      reachable only by a principal with actor_type = 'client'
/api/internal/v1/...    reachable only by a principal with actor_type = 'staff'

A shared route that "hides fields for clients" makes leakage a serialization bug — invisible in review, easy to reintroduce, and impossible to test exhaustively. Two namespaces make it a routing bug: loud, greppable, and coverable by a test that walks every client route and asserts a forbidden key appears at no nesting depth (§16).

8.3 Enforcement rules

  1. Every route declares its policy, or the app does not boot. A startup assertion walks the router and fails if any handler lacks an { action, resourceLoader } annotation. This is the one control that survives "someone added an endpoint on a Friday".
  2. Scoped fetch, never fetch-then-check. currentOrg.revisions.find(id), not Revision.find(id) followed by an authorization call. Fetch-then-check fails open when the second line is forgotten; scoped fetch fails closed.
  3. Deny returns 404 for cross-tenant objects. A 403 confirms the object exists.
  4. No mass assignment. Request bodies bind to explicit input DTOs. organization_id, role, audience, lifecycle_state and every price field are structurally unreachable from a request body.
  5. Outbound schema validation. Client-facing response types are declared additionalProperties: false in the OpenAPI schema and validated at runtime — failing the response in non-production, alerting in production.
  6. Idempotency keys on submit, derive, clone and invite. A double-click must not produce two submissions.
  7. Every deny is an audit event, not just a log line.

8.5 Interoperability posture

Do not build EDI or cXML now. Do shape the intake schema so that a later mapping is mechanical rather than a rewrite: line-level buyer_part_id / supplier_part_id, ISO 4217 currency, ISO 8601 dates, UN/CEFACT unit-of-measure codes, and a quote-level valid_until. If a client large enough to run Ariba ever appears, cXML QuoteRequest maps onto the submission and QuoteMessage / X12 843 maps onto the response. Knowing the target shape costs nothing today.

09Client-visible versus internal-only

9.1 The structural rule

The decision that matters most in this document

Internal commercial data lives in physically separate tables whose row-level security policy additionally requires actor_type = 'staff'. It is not a column on a shared row that gets filtered out on the way to the client.

This converts "did we remember to strip a field?" — a serialization bug, invisible in code review, silently reintroduced by any new column — into "did we join a table we should not have?" — a query bug, visible in review, catchable by a test that greps for a table name, and blocked at the database even if the query is written.

9.3 The preliminary-output rule

Every client-facing plan, elevation and export carries the watermark and the disclaimer, and the status is made physically inseparable from the artifact — not a footer toggle. That means: a diagonal watermark across every page; a title-block status field; the P revision code; a filename convention (…_P01_PRELIMINARY.pdf); the status text repeated inside the drawing frame, because PDFs get screenshotted and re-cropped; and a distinct colour treatment so a printed copy is identifiable across a room.

PRELIMINARY
Standing disclaimer — carried on every client-facing output, versioned by disclaimer_version_id

PRELIMINARY PLANNING AND QUOTE-REQUEST DOCUMENT. This material is for conceptual layout and estimating discussion only. It is not an installation drawing, engineered design, approval, or certification. Final scope, equipment selection, site conditions, manufacturer requirements, engineering where required, and applicable authority approvals remain subject to review.

The disclaimer text is versioned and the generated document stores which version it carried. Disclaimers get revised, and in two years someone will need to know exactly what a 2026 output said.
